# selenium-java-bdd-testing

BDD test suite for [Swag Labs](https://www.saucedemo.com/), Sauce Labs' free
demo e-commerce app used for Selenium/Cucumber practice: login, product
listing, cart, and checkout.

Standard Maven + Selenium WebDriver + Cucumber-JVM + JUnit 5 project layout,
with the Page Object Model.

## Running

```
mvn test
mvn test -Dcucumber.filter.tags="@smoke"
mvn test -Dcucumber.filter.tags="@regression and not @negative"
```

Headless mode is **off** by default - set `headless=true` in
`src/test/resources/config.properties`, or pass `-Dheadless=true` (which is
what both CI pipelines do). `WebDriverManager` downloads/caches the matching
chromedriver automatically, no manual driver setup required.

## CI

Both pipelines run `mvn -B test -Dheadless=true`:

- **GitHub Actions** - `.github/workflows/tests.yml`. Runs on pushes to
  `main`, on pull requests, and on manual dispatch, on `ubuntu-latest` with
  Temurin JDK 11 (Chrome is preinstalled on the runner). Uploads
  `target/cucumber-reports/` and `target/surefire-reports/` as the
  `test-reports` artifact, even when the run fails.
- **Jenkins** - `Jenkinsfile`. Needs an agent with JDK 11+, Maven and Google
  Chrome on the `PATH` (Linux or Windows), plus the Timestamper plugin for
  `timestamps()`. Publishes per-scenario results from
  `target/cucumber-reports/cucumber.xml` via the `junit` step and archives
  both report folders. On a Docker agent running as root, Chrome
  additionally needs `--no-sandbox`, which `DriverFactory` does not add.

## Reports

Every `mvn test` run writes these reports, from two different sources:

- `target/cucumber-reports/report.html` - **the one with real detail**:
  every feature/scenario/step, pass or fail, with failure screenshots
  embedded. Generated by Cucumber's own `html` plugin (see
  `TestRunner`'s `@ConfigurationParameter`), straight from Cucumber's event
  bus.
- `target/cucumber-reports/cucumber.xml` - the same results as JUnit XML
  (Cucumber's `junit` plugin, one `testcase` per scenario), with real
  counts. This is the file CI test-result views should read (Jenkins'
  `junit` step does).
- `target/surefire-reports/surefire-report.html` - Maven's standard build
  report (`maven-surefire-report-plugin`, bound to the `test` phase via
  `report-only`). Useful as a build-level pass/fail signal (a failed
  scenario still fails the Maven build), but **it will always say
  "Tests run: 0"** for `TestRunner` - see the javadoc on `TestRunner` for
  why: `@Suite` runs Cucumber through its own embedded JUnit Platform
  Launcher session, and those execution events never reach Surefire's
  listener. Confirmed straight from Surefire's own console summary, not a
  misconfiguration on our end.

## Layout

```
pom.xml
Jenkinsfile                   Jenkins pipeline (headless mvn test + reports)
.github/workflows/tests.yml   GitHub Actions workflow (headless mvn test + reports)
src/test/java/com/example/saucedemo/
  runner/            TestRunner.java - the JUnit 5 Suite entry point (@IncludeEngines("cucumber")); sets glue + report plugins
  pages/             Page Object Model: BasePage + one class per screen
  stepdefinitions/   Cucumber step definitions + Hooks (driver lifecycle, failure screenshots)
  util/              DriverFactory, ConfigReader, SortOptionMapper - plain helper classes
src/test/resources/
  features/          *.feature files (Gherkin)
  config.properties  base.url, browser, headless, wait timeout
  log4j2.xml         logging config
  junit-platform.properties   parallel-execution config (4 threads, fixed) + publish.quiet
```

## Tags

`@smoke` fast subset, `@regression` full functional coverage, `@negative`
error-path scenarios.

## Notes on the target application

Swag Labs (saucedemo.com) is a public sandbox built for Selenium practice.
It ships several accounts with intentionally broken behavior
(`locked_out_user`, `problem_user`, `performance_glitch_user`,
`error_user`, `visual_user`) alongside the well-behaved `standard_user` this
suite uses; the shared password for all of them is `secret_sauce`.

Scenarios run in parallel across feature files (`junit-platform.properties`)
- `DriverFactory` hands each test thread its own `WebDriver` via
`ThreadLocal` for exactly that reason.
